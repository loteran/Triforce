# Hookshot (oot-recomp)

**Hookshot** is the port's name (as Skybound is TOTKPort's and BlueShell is mkw-recomp's); the maintainer's repository
folder stays `oot-recomp`. The game builds as `hookshot.exe` + `hookshot_vk.dll` (`hookshot` + `hookshot_vk.so` on Linux).

A static recompilation of the Switch 2 *The Legend of Zelda: Ocarina of Time* remake to native x86-64 Windows and Linux:
the game's code lifted to C (NotRexed's a64-kit, Rexcomp's AArch64 kit), the Horizon OS and NVN2 implemented
natively, the GPU work replayed on Vulkan. It is a fork of mkw-recomp (`..\mkw-recomp`, Mario Kart World), whose
paths it keeps so MKW's fixes apply here.

**No game files are in this repository.** The dump is read where it lies (`work/dump.txt`); everything made from it
(modules, image, lifted C, builds, runs) goes to `work/`, which git ignores.

Status: the game plays; the README's [status table](../readme.md#project-status) says how far. The design, its stages and
the lessons carried over from MKW: [design.md](design.md).

## Use

Requirements: Python 3 with `pip install -r requirements.txt` (`lz4`, `numpy`, `capstone`, `unicorn` 2.1,
`zstandard`, and the button-prompt packages); a compiler: on Windows llvm-mingw
(`HOOKSHOT_MINGW`, or an `llvm-mingw` folder in the clone), else emsdk's clang at `C:\emsdk` (or `EMSDK`) with Visual
Studio's C++ tools; on Linux clang and lld. For the Vulkan back end: distro Vulkan / SPIR-V / VMA headers under
`/usr`, or `HOOKSHOT_VULKAN_HEADERS` / `HOOKSHOT_SPIRV_HEADERS` / `HOOKSHOT_VMA_HEADERS`, or a CPM package cache
(`RX_CPM`, else `cpm` in the clone, else the old caches in mkw-recomp's `work/eg` or `..\Eglantine\.cache\cpm`).
Without those the standalone build stops. [CONTRIBUTING.md](../CONTRIBUTING.md#development-setup) has the rest.

Run everything with `python -I` from this folder.

| Command | What |
|---|---|
| `python -I nx2/nup.py <file.nup> --extract work/dump` | the `.nup` dump package to `work/dump/exefs` + `romfs` (newest title; ZBIC NSOs made plain by `nx2/unpack.py`) |
| `python -I nx2/dump.py --dump <folder with exefs/ and romfs/> --set` | what the dump is (Switch 1 or 2, ids, modules, SDK, NVN); `--set` records it in `work/dump.txt` |
| `python -I nx2/lift.py [--write]` | image + discovery + coverage (`work/image/coverage.txt`); `--write` emits the C to `work/gen` |
| `python -I nx2/census.py --nx2` | instruction census per module, after the Switch 2 forms |
| `python -I nx2/test_insn.py [--per 6 --states 12]` | every instruction form the game uses, Unicorn vs lifted C |
| `python -I nx2/test_leaf.py [--count 3000 --states 4] [--calls]` | random whole functions (or call trees), Unicorn vs recompiled native code on the real image |
| `python -I nx2/lift.py --standalone --write` then `python -I nx2/build.py --standalone --jobs 4` | the standalone game: `work/sa/build/hookshot.exe` + `hookshot_vk.dll` |
| `powershell -File scripts/run-vk.ps1 [-Window] [-Seconds 120] [-Name x]` | a muted test run on Vulkan, with screenshots in `work/runs/<name>/shots` |
| `python -I scripts/prof.py <stacks file>` | a profile sampled with `HOS_PROFILE=<seconds>` + `HOS_SAMPLE=<thread>` + `HOS_SAMPLE_FILE=<stacks file>` (the sampler runs only with `HOS_PROFILE` set), named from the linker maps |

The dump can also come from `OOT_DUMP` (its folder) or `OOT_EXEFS`; `OOT_WORK` moves the work folder.

The built game's own arguments (`image.bin`, `--romfs`, `--user`, `--trace`, `--prepare-shaders`) are in the README's
[Running the game from the command line](../readme.md#running-the-game-from-the-command-line).

Scripted test input (`HOS_INPUT_SCRIPT` and `HOS_INPUT_LIVE`) is applied before the window-focus check. A log saying
the game window is not in front does not mean those presses were discarded. `HOS_HEADLESS` and
`HOS_WINDOW_NOACTIVATE` change window creation, not this input routing. The game must still reach a state that reads
and responds to the supplied controller input.

Physical keyboard and mouse input stays with the foreground window. Physical controllers can also play in the
background when the existing "Controller in background" option or `HOS_INPUT_BACKGROUND=1` enables them;
`HOS_INPUT_BACKGROUND=0` overrides that option. With `HOS_INPUT_EXCLUSIVE` set (to any value, `0` too) the script
alone drives the game until 5 s after its last press; without it the player's devices add to the script's presses. It
is not a focus override.

## Switches for testing and debugging

The running game reads its switches from the environment or from `hookshot_env.txt` beside `image.bin` (one
`NAME=VALUE` a line, `#` for notes; `HOS_ENV_FILE=<path>` reads that file instead). The build reads its own from the
environment. The README has the ones players are asked to try (`RX_VK_ASTC_RGBA8`, `RX_VK_LOW_SPEC`,
`RX_VK_MOVIE_UPSCALE`, `RX_VK_SKIP_CODE`, `HOS_OOT_CHEATS`). There are several hundred more, most of them one-off
experiments: `grep -rn 'getenv("' host gpu/vk` lists them, and the comment where each is read says what it does.
"Set" below means any value, `0` included.

`RX_VK_MESH_NOCULL=<prefix,...>` turns off the culling in the task shaders whose native code key starts with one of
the prefixes. On a Steam Deck, `RX_VK_MESH_NOCULL=2c56dc1006942f74` avoids the same hang without leaving anything out:
that task shader walks a coarse depth grid cell by cell for every meshlet and ends with
`visible = (result & 1) | (c3[2320] & 4)`, bit 4 being the game's own "draw everything". The switch makes that answer
true, and dead code elimination removes the grid walk, so every meshlet is drawn and the rasterizer clips what is off
screen. It costs some GPU time on cards that cull quickly, so it is off unless set. The log says
"culling off, every meshlet drawn" for each task shader it changed.

### Input for scripted runs

| Switch | What it does |
|---|---|
| `HOS_INPUT_SCRIPT=<presses>` | Presses timed from the game's first controller read |
| `HOS_INPUT_LIVE=<file>` | A file the test appends lines of presses to, read every 30 ms; each line's times count from when it is read. A line `!cheat <n>` sends a Cheats page action, `!synclog` logs the NVN syncs (`!dump`, `!shots`, `!rdoc` and `!flasharm` are the WebGPU renderer's) |
| `HOS_INPUT_FRAME_CLOCK=1` | The script's time runs at 60 game frames a second instead of the wall clock |
| `HOS_INPUT_EXCLUSIVE`, `HOS_INPUT_BACKGROUND`, `HOS_INPUT_SCRIPT_BACKGROUND` (set) | As above; the last lets every device count while the window is behind another one |
| `RX_VK_MENU_SCRIPT=<seconds>:<key>,...` | Timed Insert menu keys: `INS`, `UP`, `DOWN`, `LEFT`, `RIGHT`, `ESC`, `ENTER`, `TABL`, `TABR` |
| `RX_VK_UI_PROMPTS=pad` or `keys` | The menu's button prompts for a controller or the keys, whatever was used last (screenshots) |
| `RX_VK_UI_GAME_FONT=0` | The menu, the counter and the start-up screen in the included Libertinus, not the game's own font |

The presses are `<seconds>:<button>[+<button>...][/<ms>]`, separated by commas, for example `2:A,5.5:LUP/1500,9:ZL+R`.
The buttons are `A B X Y L R ZL ZR PLUS MINUS LS RS LEFT UP RIGHT DOWN`, and the sticks pushed to their edge `LUP
LDOWN LLEFT LRIGHT RUP RDOWN RLEFT RRIGHT`. A press is held for 200 ms unless `/<ms>` says otherwise. The names are
case-sensitive, and an unknown one is ignored.

### Building

A build reads and writes tens of gigabytes. When the game folder or the build files folder is on a hard drive,
`make_game.py` warns that an SSD is much faster and builds anyway (the builders ask before they start).

| Switch | What it does |
|---|---|
| `HOOKSHOT_JOBS=<n>` (or `--jobs`) | Compilers at once (default one per CPU thread, each started when the free memory holds it; `HOOKSHOT_MEM_GATE=0` turns that check off) |
| `HOOKSHOT_LIFT_JOBS=<n>` | Processes that write the lifted C. Forked on Linux and macOS: default the cores, at most 16, one per 2 GB of free memory. Spawned on Windows (`nx2/emit_pool.py`), where they also cut the big chunks and share the page marks: default half the processors, at most 8, one per GB of free memory. `1`: one process, on every system; the C is the same whatever the count |

| `HOOKSHOT_EARLY_COMPILE=0` | (Windows) Not compiled beside the lift: libopus and the two renderers, which need no translated code. | `HOOKSHOT_MEM_GIANT=1` or `0` | Whether the memory gate counts a function of 1.2 MB or more by the square of its size (a chunk that is one 5 MB function takes 6.2 GB, not the 1.9 GB it is counted at otherwise). ## Mods: code patches and cheats

The game loads RomFS mods at its start (`host/mods.c`). The two kinds of mod that change what the game *does* go other
ways, because the game's code is C compiled ahead of time and cannot be patched while it runs.

**The mods folder**, for the game and for a build alike (`host/mods.c` `find_mods`, `nx2/code_mods.py` `find_mods`,
which must stay the same walk): a mod is a folder under `mods` that holds a `romfs`, `exefs` or `cheats` folder, at
most four levels down, and nothing below a mod is looked at. A folder whose name starts with `-` or `_` is off, one
that starts with `.` is skipped. Mods are ordered by their path under `mods`, ASCII letters' case ignored, and the last
one wins. Triforce Setup's mod manager can switch a mod by renaming its folder and order mods by a prefix, and needs
no other file.

**Code patches** (`<mod>/exefs/*.ips`, `*.pchtxt`), `nx2/code_mods.py`:

- `make_game.py` calls `build_step` once its copy of the game's code (`<work>/exefs`) is there and checked, after the
  copy the game folder keeps for updates (`.triforce_exefs`) is made and before the lift key is taken. The patches go
  into that copy, a module with a patch written again as a plain NSO, and the lift reads it: `lift.py`, `chunks.py`
  and the rest of the translator know nothing of mods.
- The lift key hashes the files of that copy, so the patched bytes are in it: a patch added, taken out, switched off
  or edited translates the game again, a patch that changes no byte does not, and neither does a change to
  `code_mods.py` itself (`LIFT_KEY_NOT`).
- A patch names its module by build id (the `.ips` file's name, the `.pchtxt` file's `@nsobid-`, trailing zeros left
  out or not) and may be for any module of the exefs. Offsets count the NSO's 0x100-byte header, as Atmosphere and the
  emulators read them; `.pchtxt` knows `@flag offset_shift`, `@enabled`, `@disabled`, `@little-endian`, `@big-endian`
  and `@stop`. Mods in order, a mod's files by name, the later write wins and the build says which file wrote over
  which.
- A file is refused whole, with a line that says why: another build's, cut short, a value that cannot be read, a write
  into the header, past the image or between the segments. The last leaves out code caves, which the translator has
  not been tried on.
- The build writes `triforce_code_mods.txt` into the game folder when it is done: a line per patch file, tab
  separated, `applied` or `refused`, the file's FNV-1a 64 and size, its path under the mods folder, then the module
  and the bytes changed, or the reason. The next build (the game's update offer runs `--update`) reads the mods folder
  again, so the same patches are built in again, and says which of the record's are gone, changed or refused now. The
  game reads the record at its start (`host/mod_code.h`) and logs for each patch file whether it is built in or waits
  for a build, and which built-in patches are gone from the folder.

**Cheats** (`<mod>/cheats/<first 16 digits of main's build id>.txt`), `host/mod_cheats.h` and `host/mod_cheats.c`:

- Read at the start, run by an interpreter once a game frame, at the game's present and on its thread
  (`hos_mod_cheats_frame`). Nothing is compiled in, so a cheat file needs no build. NX2navi compiled in the cheats that
  write instructions; Triforce's translator has no switchable patches, so such a cheat (an opcode 0 into a module's
  `.text`) is refused and belongs in a code patch.
- The opcodes it runs are listed at the top of `host/mod_cheats.h`: 0 to A and C0 to C3 of Atmosphere's cheat machine.
  Any other is refused when the file is read, the whole cheat, by name. Registers are shared by one file's cheats within
  a frame and cleared between frames; a master code runs first.
- Memory is the program image and the heap, each access checked (`mod_cheat_readable`); the modules' code
  (`hos_code` in the generated `hos_image.c`) is never written. Region 0 is the module main's base (`hos_main_base`),
  1 and 2 `HOS_HEAP_BASE`, 3 `0x08000000`, as `host/hos_svc.c` tells the game.
- Each cheat that is not a heading has a row on the System tab, 96 at most (`gpu/vk/mod_cheat_rows.h`; option ids 130
  to 133 in `gpu/vk/vk_api.h`). The rows are not in the options file: `triforce_cheats.txt` in the game folder has a
  line for each cheat that is on, its number (FNV-1a 32 of `<mod>/<name>`) and that text, and a cheat listed there is
  on at the start.

`microphone_device=<name>` when a microphone is chosen by name, and the controls (`pad_<button>` and `key_<button>`:

menu rewrites in place (`gpu/vk/game_language.h`: the code alone on that line, the rest of the file as it was, and only a
code the file itself names) and the host reads at the start (`host/nn_applet.c`). Nor are the Mod cheats rows: which
of a mod's cheats are on is the host's to keep, in `triforce_cheats.txt` (*Mods: code patches and cheats* above).

(Triforce) `options_version=8` grouped the rows and merged those that chose one thing twice (`gpu/vk/merged_rows.h`; the
436f9ac-based builds wrote 7 for it, which v0.5.1 had already given to Frame pacing's default: its 7 still has the old rows'
lines, so a file before 8 is moved, and one of those builds' 7, without them, keeps what it has). A file
from before keeps its values; these lines are read once and not written again, their rows' jobs done otherwise:
`quality_preset` (the textures' and the mirrors' memory budgets are the card's own, from its video memory), `upscaling`
(the window's filter follows the sizes: `gpu/vk/upscaler_rows.h` `auto_filter`, AMD FSR 1 when the picture is enlarged, the
plain copy otherwise and always with HDR Native), `reflex_frame_limit` (off, the old default, until Reflex holding the cap
with DLSS frame generation has been played: `RX_VK_REFLEX_LIMIT=1` for a run), `handheld_profile` (an `output_res`) and `stick_dead_zone` (each
stick's own).

The other rows are 0 Off and 1 On. Some are read at the start, before the menu exists, by the code that needs them:
`output_res` (`host/nn_applet.c`; 7 is the handheld profile), `ultrawide` (`host/hos_main.c`), `frame_rate_cap`
(`host/nn_vi.c`; the monitor's rate is the display's the window opens on, rounded, 30 to 240, and 60 when it cannot be read), `robust_buffers`
(`gpu/vk/vk_main.cpp`), `texture_detail` (`gpu/vk/vk_texture.cpp`, at the first texture) and the controls (`host/nn_hid.c`).

The `renodx_` rows other than `renodx_hdr` are read at every frame (`gpu/vk/vk_renodx.cpp` `fill_settings`), and the
menu shows the rows of one tonemapper while it is the one chosen. RenoDX's mod for this game has Vanilla and PsychoV35;
RenoDRT and the gamma correction come from `gpu/vk/shaders/renodx_glue`, three files of Triforce's own that
`scripts/renodx_shaders.py` compiles together with RenoDX's scene shaders and its output encoder as the build fetched them
(nothing of RenoDX is in the repository or changed). RenoDRT calls RenoDX's library; the gamma correction is on the
finished picture, HUD included, and the tone mappers are given a peak with it taken out, so that the brightest light
still lands on the HDR peak brightness. A change to a glue file changes the stamp of `renodx_spv.h`, which the next build
then compiles again.

RivaTuner Statistics Server has no row: where it is installed and running it is the game's frame limiter, and an options
file that still has the test builds' `rivatuner_limit=` is read by nothing (the next save drops the line). A thread of
`gpu/vk/rtss_limit.cpp` looks twice a second: it puts the limit (`gpu/vk/pace_rule.h` `pace_rtss_want`: the cap in
effect, Monitor's rate and the caps under 60 included, times the frames shown for each of the game's with frame
generation 2x to 8x or AMD FSR 4) into RTSS's profile for the executable through RTSS's own hooks library
(`RTSSHooks64.dll` from RTSS's folder: `FramerateLimit` and `FramerateLimitDenominator`, nothing else, no other profile),
reads it back, and once RTSS is seen holding the game to it (`gpu/vk/rtss_decide.h` `rtss_decide`) the host's wait steps
aside (`gpu/vk/vk_pace.cpp`), the in-house frame generation's display thread leaves its own spacing of made frames to
RTSS, and Reflex is given no frame limit. A limit lower than the profile's waits 5 s before it is written, a higher one
1 s, so a multiplier that changes in play does not rewrite the profile each time. What the profile held is kept in
`triforce_rtss_profile.txt` in the game folder before the first change (one line per executable, the others' lines
kept, a file that does not read left alone) and goes back at the exit; the next start puts it back after a kill or a
crash, unless the player changed the profile since. The game's own wait holds the frames instead with frame generation
on Auto (its presents follow the screen's refresh, not the game, so no limit on them holds the game) and with DLSS frame
generation (Streamline presents on a pace of its own: `HOS_RTSS_DLSSG=1` tries RTSS there), during movies (the profile
keeps the play limit), while no picture went out for 200 ms (a minimised window), while RTSS is not installed, not
running or has not hooked the game, and when the profile does not keep the limit (no administrator rights) or RTSS
refuses it, unless a limit the player set in RTSS, at or under the game's, holds the game (then RTSS holds movies too).
A hold needs a present since the frame start two frames back, so a window that stops showing gives the frames back
within two frames. RTSS's count past 1.05 times the limit three
periods running, 30 s hooked with the limit and no hold, or the game's frames coming sooner than the cap give the frames
back; RTSS is tried again a minute later (three times), and at once when RTSS starts again or another limit is wanted.
The game never starts RTSS, installs nothing and asks for no rights. `vk: pace:` lines in the log say which limiter is in
force and why; the Full overlay's Frame limit line names RivaTuner or NVIDIA Reflex after the rate when either holds the frames.
